# Rebuild Accordion and Collapsible on `<details>`/`<summary>`

**Status:** proposed — ready for implementation, with one gate that can veto Phase 3 (§3.3).
**Motivation:** no component in the catalog uses `<details>`. `Accordion` and `Collapsible` are
hand-rolled signal FSMs whose panels are unreachable with JS disabled, which contradicts the
native-first substrate rule in `CLAUDE.md` and puts both at `clientJs: 'required'`
(see [`client-js-manifest-field.md`](../specs/client-js-manifest-field.md)).
**Outcome:** both render open/closed state at first paint, work with JS off, gain find-in-page
expansion for free, and move to `clientJs: 'enhancement'`.

---

## 1. Verified constraints

Everything below was checked empirically — jsdom probes run through
`vp run @cascivo#components#test`, browser support from current support data. Do not re-litigate
these during implementation; do re-verify if the toolchain moves.

### 1.1 jsdom does not give us the semantics the current tests assert [verified]

| Probe                                                    | Result                       |
| -------------------------------------------------------- | ---------------------------- |
| `getByRole('button', { name })` on a `<summary>`          | **NOT FOUND**                |
| `summary.getAttribute('aria-expanded')`                   | **`null`** — state is native |
| `<details name>` exclusivity (click B while A is open)    | **not implemented** — both stay open |
| `toggle` event on click                                   | fires                        |
| `<summary><h3>Title</h3></summary>` → `getByRole('heading')` | found                     |
| `<details>` → `getByRole('group')`                        | found                        |

Consequences, all load-bearing for the plan:

- **Every existing test breaks.** `accordion.test.tsx` and `collapsible.test.tsx` query
  `getByRole('button', …)` and assert `aria-expanded`. Both idioms are gone. Tests must be
  rewritten against `details.open` and visibility, not rewritten to force the old assertions back.
- **Exclusivity cannot be delegated to the browser in tests.** `type="single"` must still be
  enforced in the JS layer, exactly as today. Native `name=` is then a *no-JS bonus*, not the
  mechanism. Do not delete the JS exclusivity logic.

### 1.2 Browser support is adequate, animation support is not [verified]

| Feature                                   | Status                                              |
| ----------------------------------------- | --------------------------------------------------- |
| `<details name>` (exclusive)              | Chrome 120+, Edge 120+, Firefox 130+, Safari 17.2+  |
| `::details-content`                       | Baseline newly available since Sept 2025, all major |
| `transition-behavior: allow-discrete`     | Baseline since Aug 2024                             |
| `interpolate-size` / `calc-size()`        | **Chromium only**                                    |

The first three clear the "last 2 versions of Chrome, Firefox, Safari" target in
`docs/COMPATIBILITY.md`. `interpolate-size` does not, so it is progressive enhancement only under
the CSS rules in `CLAUDE.md`.

### 1.3 `apg:check` reads the manifest, not the DOM [verified]

`scripts/checks/apg.test.ts` asserts `accessibility.role` includes one of the pattern's
`requiredRoles` and `keyboard` covers `requiredKeys`, reading from `registry.json`. Both
`accordion` and `disclosure` require `role: 'button'` + `Enter`/`Space`.

`<summary>`'s implicit ARIA role **is** `button` per HTML-AAM, and Enter/Space activate it
natively. So the manifests stay truthful and unchanged, and `apg:check` keeps passing without
touching `scripts/checks/apg/patterns.ts`. Only the jsdom *queries* need to change. **Do not add
`role="button"` to `<summary>`** to make the old query work — it overrides the native disclosure
mapping and suppresses expanded-state announcement in some AT.

| ---------------------------------------------------------- | --------------------------------------------- |

## 2. The two tradeoffs, stated before the plan

Neither is a blocker, both are real, and the second is why Phase 3 has a veto gate.

**Exclusive accordions.** Patrick Brosset's 2026 accordion writeup deliberately avoids `name=`,
noting "mutually exclusive accordions are not accessible" — content can vanish from under the user
with no warning. cascivo already ships `type="single"` as the **default** and already behaves
exclusively, so adopting `name=` changes nothing about the JS-on experience; it only makes the
JS-off experience match. Adopt it, scoped to `type="single"`, and leave the default alone. This is
not a new a11y decision, just a newly honest one.

**The heading wrapper.** This is the real cost. APG's accordion pattern wants each header to be a
heading element *containing* a button, which is what ships today (`<h3><button>` in
`accordion.tsx:118-120`). `<summary>` must be the first child of `<details>`, so `<h3><summary>` is
impossible. The options are `<summary><h3>Title</h3></summary>` (valid HTML — `summary`'s content
model permits heading content — but nests a heading inside a button-role element, with mixed AT
support) or dropping the heading entirely (loses heading-navigation for screen-reader users, a
straight regression).

Plan assumes **heading inside summary**, and Phase 3.3 is the gate that can reverse it.
`Collapsible` is unaffected — a plain disclosure has no heading requirement, so it is a clean win.

## 3. Implementation

### Phase 1 — `Collapsible` (the clean case, do this first)

It has no heading requirement, no exclusivity, and no internal consumers. Land it as the pattern
the Accordion follows.

1. **Rewrite `collapsible.tsx`.** `<details>` replaces `.root`, `<summary>` replaces the trigger
   `<button>`, content moves inside `<details>`. Keep the `trigger`, `open`, `defaultOpen`,
   `onOpenChange`, `disabled`, `className` props exactly as-is — the public API does not change.
   → verify: `pnpm dead-props:check` (every declared prop still read)

2. **Handle the controlled-`<details>` desync.** React tracks the `open` prop against its own last
   render, but a user click mutates `details.open` in the DOM behind React's back. When the signal
   round-trips to the same value React last rendered, React issues no DOM update and the element
   stays stuck. Do **not** rely on `<details open={isOpen}>` alone. Drive it imperatively:

   ```tsx
   const detailsRef = useRef<HTMLDetailsElement>(null)
   useSignalEffect(() => {
     const el = detailsRef.current
     if (el && el.open !== openSig.value) el.open = openSig.value
   })
   ```

   `openSig` is already a signal from `useControllableSignal`, so no prop mirroring is involved and
   the `useEffectPropSignal` rule in `CLAUDE.md` does not apply here. `data-state` is still read in
   render, which is why the signal stays render-visible.
   → verify: a test that clicks twice and asserts `details.open` returns to its starting value

3. **Wire the `toggle` event**, not `onClick`. `onToggle` fires after the browser has already
   changed state, so the handler reports rather than drives:
   `onToggle={(e) => setOpen((e.currentTarget as HTMLDetailsElement).open)}`.
   → verify: `onOpenChange` fires once per toggle, with the right boolean

4. **`disabled` has no native equivalent on `<details>`.** Implement as
   `onClick={(e) => { if (disabled) e.preventDefault() }}` on the `<summary>`, plus
   `aria-disabled="true"` and the existing `:disabled` styling moved to `[aria-disabled='true']`.
   Note in the manifest that `disabled` is enforced in the enhancement layer — with JS off a
   disabled Collapsible is still operable. That is an honest degradation and must be documented,
   not hidden.
   → verify: test asserts a disabled Collapsible does not open on click

5. **CSS.** Rewrite `collapsible.module.css` per §4.

### Phase 2 — `Accordion`

1. **Map the compound API onto the element.** The current shape already matches: `AccordionItem` →
   `<details>`, `AccordionTrigger` → `<summary>` (first child), `AccordionContent` → the sibling
   that `::details-content` wraps. **No consumer markup changes**, which is what keeps
   `blocks/faq/faq.tsx` untouched.

2. **Keep both context providers and the `.Consumer` render-prop form.** They exist because
   `useContext` is banned by `CLAUDE.md`; that constraint is unchanged. Note that `createContext`
   is unavailable under the `react-server` condition, so `Accordion` stays a client component
   regardless — the win here is `required` → `enhancement`, not `→ none`.

3. **Keep the JS exclusivity logic in `store.toggle` verbatim.** Per §1.1 jsdom will not do it, and
   with JS on it is what actually drives state. Add `name={type === 'single' ? baseId : undefined}`
   on the `<details>` purely for the no-JS case. The two do not fight: the browser mutates the DOM,
   the `toggle` handler observes, React re-renders from the signal.
   → verify: existing "closes the open item when another opens in single mode" behaviour, rewritten
   per §1.1, still passes

4. **`AccordionTrigger` renders `<summary><h3 class={styles.heading}>{children}</h3></summary>`.**
   Keep the `forwardRef`, retargeted from `HTMLButtonElement` to `HTMLElement` (the `<summary>`).
   **This is a public type change** — update `apps/site/src/shims/accordion.d.ts` to match.

5. **Drop the manual `aria-expanded` / `aria-controls` / `id` wiring on the trigger.** Native
   `<details>` conveys expanded state; a hand-set `aria-expanded` on `<summary>` duplicates and can
   conflict with it. Keep `role="region"` + `aria-labelledby` on the content wrapper — that is
   additive and does not collide with native semantics. `useId` is still needed for the region
   labelling and for the `name` group id.

## 4. CSS

Both components share one structure, so write it once and mirror it.

**Animation.** The current `grid-template-rows: 0fr → 1fr` trick animates in every target browser.
`interpolate-size` would be simpler but is Chromium-only (§1.2), so it must not be the primary
mechanism. Keep the grid trick, applied to `::details-content`, with `content-visibility` sequenced
by `transition-behavior: allow-discrete` so the browser does not hide the content before the
collapse finishes:

```css
.item::details-content {
  block-size: 0;
  overflow: hidden;
  transition:
    block-size var(--cascivo-duration-200) var(--cascivo-ease-out),
    content-visibility var(--cascivo-duration-200) allow-discrete;
}
.item[open]::details-content {
  block-size: auto; /* static fallback — jumps in FF/Safari */
}
```

**This exact sequencing is the one thing in the plan I could not verify statically — prove it in
the bare-page harness before committing to it.** If `::details-content` + grid rows does not
transition cleanly, fall back to animating an inner wrapper element (which `AccordionContent`
already provides as `.contentInner`) and keep `::details-content` for padding only.

Then, and only then, layer `interpolate-size` as the Chromium enhancement, with the static
fallback immediately preceding it in the same rule block, per the `@function`/`if()` discipline in
`CLAUDE.md`.

**Closed-state box hazard.** Authoring `display: grid` on `::details-content` risks overriding the
UA's closed-state hiding — structurally the same bug `pnpm popover:check` was written to catch ("a
closed popover keeps no box — an author `display` beats the UA hide rule"). Verify a closed
`<details>` contributes no box. If this proves fragile, a small `details:check` guard in the same
shape as `popover:check` is warranted; do not add one speculatively.

**Marker.** Remove the UA disclosure triangle (`.trigger::-webkit-details-marker { display: none }`
plus `list-style: none`) and keep the existing `.indicator` span, switching its open selector from
`[data-state='open']` to `[open] &`.

**Layers.** Everything stays inside `@layer cascivo.component`; the existing
`@media (forced-colors: active)` and `(prefers-reduced-motion: reduce)` blocks stay top-level and
unlayered, which is the sanctioned exception.
→ verify: `pnpm layers:check && pnpm unlayered:check && pnpm breakpoint:check`

## 6. Out of scope

- **`clientJs` itself.** Specced separately; Phase 4.1 consumes it and waits on it.
- **Other disclosure-shaped components.** `NavigationMenu`, `SideNav`, and `OverflowMenu` are menu
  patterns with roving focus, not disclosures. `<details>` is wrong for them.
- **Removing `'use client'`.** Both stay client components (§2 Phase 2.2).
